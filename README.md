# avr-fota

Универсальная прошивка для **ESP8266** и **ESP32** с веб-интерфейсом, предназначенная для программирования микроконтроллеров по локальной сети, а также для удалённого управления устройствами.

Проект построен по **модульной архитектуре**: есть набор **ядер (core)** — обязательных модулей, которые присутствуют в любой сборке, и **подключаемые модули**, которые добавляются через конфигурацию таргета в `platformio.ini` и ini файлы в папке targets.

## Архитектура проекта

Проект разделён на две категории модулей:

### Ядра (core)

Ядра — это модули, которые **всегда присутствуют** в прошивке независимо от выбранного таргета. Они обеспечивают базовый функционал устройства.

В основе архитектуры проекта используется **EERTOS** — кооперативный диспетчер задач и таймеров (не является операционной системой). EERTOS обеспечивает циклический вызов задач и работу программных таймеров без использования прерываний.

| Модуль | Директория | Назначение |
|--------|-----------|-----------|
| **core_wifi** | `src/core_wifi/` | Wi-Fi клиент/точка доступа, управление 4 профилями подключения, сканирование эфира |
| **core_ntp** | `src/core_ntp/` | NTP клиент с поддержкой 3 серверов (основной + 2 резервных), автоматическое переключение |
| **core_ota** | `src/core_ota/` | Самообновление прошивки ESP (FOTA) через веб-интерфейс, проверка версий файловой системы |
| **core_json** | `src/core_json/` | Утилиты для работы с JSON-документами (сохранение/загрузка) |
| **core_led** | `src/core_led/` | LED-индикация, макросы для отображения событий (Wi-Fi, ошибки, успех, ожидание) |
| **core_terminal** | `src/core_terminal/` | Serial-терминал с набором команд для отладки и управления |

### Подключаемые модули

Подключаемые модули **не входят** в базовую прошивку. Это **опциональные модули**: они добавляются через `src_filter` в конфигурации таргета и активируются соответствующими `build_flags`. Полный реестр компонентов — в `INVENTORY.md`; для сборки нужны склонированные репозитории модулей.

> Документация каждого компонента лежит в `<component>/AGENTS.md` (по аналогии с корневым `AGENTS.md`) — это инструкции, привязанные к компоненту и читаемые агентом в контексте этого компонента. Пользовательские разделы (руководства по работе с программаторами, веб-интерфейсом и т.п.) также находятся там.

| Модуль | Директория | Флаг активации | Назначение | Документация |
|--------|-----------|---------------|-----------|--------------|
| **module_program** (ISP) | `src/module_program/` (module_prog + submodule_isp) | `-D PROGTYPE_ISP` | AVR-ISP программатор (AtMega/AtTiny) | `src/module_program/AGENTS.md` |
| **module_program** (SWD) | `src/module_program/` (module_prog + submodule_swd) | `-D PROGTYPE_SWD` | SWD программатор (STM32) | `src/module_program/AGENTS.md` |
| **module_udp** | `src/module_udp/` | `-D MODULE_UDP` | UDP-широковещание, обнаружение устройств в сети | `src/module_udp/AGENTS.md` |
| **module_editor** | `src/module_editor/` | `-D MODULE_EDITOR` | Браузер файловой системы, редактор .html/.txt/.json/.js файлов (форк Ace), загрузка/удаление | `src/module_editor/AGENTS.md` |
| **module_ds3231** | `src/module_ds3231/` | `-D MODULE_DS3231` | Часы реального времени DS3231 | `src/module_ds3231/AGENTS.md` |
| **module_gpio** | `src/module_gpio/` | `-D MODULE_GPIO` | Управление GPIO через веб-интерфейс | `src/module_gpio/AGENTS.md` |
| **module_lcd-i2c** | `src/module_lcd-i2c/` | `-D MODULE_LCD_I2C` | LCD I2C дисплей | `src/module_lcd-i2c/AGENTS.md` |
| **module_macros** | `src/module_macros/` | `-D MODULE_MACROS=1` | Макросы/сценарии (Lua), только ESP32 | `src/module_macros/AGENTS.md` |
| **module_otaclient** | `src/module_otaclient/` | `-D MODULE_OTACLIENT=1` | OTA-клиент (получение обновлений с удалённого сервера) | `src/module_otaclient/AGENTS.md` |
| **module_rgb** | `src/module_rgb/` | `-D MODULE_RGB` | RGB-лента/матрица (WS2812) | `src/module_rgb/AGENTS.md` |
| **module_i2c-mapper** | `src/module_i2c-mapper/` | `-D MODULE_I2C_MAPPER` | Сканер шины I2C | `src/module_i2c-mapper/AGENTS.md` |
| **module_template** | `src/module_template/` | `-D MODULE_TEMPLATE` | Шаблон модуля — эталон для новых (входит в ядро) | `src/module_template/AGENTS.md` |

Устройства — тоже **опциональные** репозитории-«рецепты сборки»: в `.ini` перечисляют нужные модули. Для сборки необходимо клонировать само устройство и все указанные в его `.ini` модули.

| Устройство | Директория | Флаг активации | Назначение | Документация |
|-----------|-----------|---------------|-----------|--------------|
| **device_clock-mech** | `src/device_clock-mech/` | `-D DEVICE_CLOCKMECH=1` | Механические часы | `src/device_clock-mech/AGENTS.md` |
| **device_mech-ring** | `src/device_mech-ring/` | `-D DEVICE_RINGMECH=1` | Механические часы с боем | `src/device_mech-ring/AGENTS.md` |
| **device_electronica7_rgb** | `src/device_electronica7_rgb/` | `-D DEVICE_E7RGB=1` | Часы «Электроника-7» RGB (матрица) | `src/device_electronica7_rgb/AGENTS.md` |

## Таргеты (конфигурации сборки)

Конфигурации сборки (таргеты) описываются в файлах:

- `targets/targets_example.ini` — примеры готовых конфигураций
- `targets/targets_user.ini` — пользовательские конфигурации

### Примеры таргетов

**ESP32 + SWD программатор (STM32):**
```ini
[env:esp32-swd]
extends = env:esp32
src_filter = ${platformio.src_filter} +<module_program/module_prog/> +<module_program/submodule_swd/> +<module_udp/>
build_flags=
    ${env.build_flags}
    ${env:esp32.build_flags}
    -D MODULE_UDP=1
    -D PROGTYPE_SWD=1
    -D SWDPIN_CLK=21
    -D SWDPIN_DATA=19
```

**ESP32 + AVR-ISP программатор:**
```ini
[env:esp32-isp]
extends = env:esp32
src_filter = ${platformio.src_filter} +<module_program/module_prog/> +<module_program/submodule_isp/> +<module_udp/>
build_flags=
    ${env.build_flags}
    ${env:esp32.build_flags}
    -D MODULE_UDP
    -D PROGTYPE_ISP
    -D PIN_MISO=19
    -D PIN_MOSI=23
    -D PIN_SCK=18
    -D PIN_RST=5
```

**ESP8266 + GPIO модуль:**
```ini
[env:esp8266-gpio]
extends = env:esp8266
src_filter = ${platformio.src_filter} +<module_gpio/>
build_flags=
    ${env.build_flags}
    ${env:esp8266.build_flags}
    -D MODULE_GPIO=1
```

## Базовый функционал

1. Wi-Fi клиент/точка доступа;
1. Работа с одной из четырёх Wi-Fi точек доступа (далее — ТД) с индивидуальным хранением сетевых настроек каждой ТД (DHCP/статичный IP);

1. Файловая система (далее ФС);
1. NTP клиент. Возможность переключения на другой NTP сервер в случае невозможности подключения к основному (один основной + два резервных);
1. Самообновление прошивки (FOTA) ESP8266/ESP32 микроконтроллера через веб-интерфейс;
1. Браузер файловой системы и редактор .html, .txt, .json, .js файлов;
1. Защита от неавторизованных пользователей с использованием логина и пароля;
1. **AVR-ISP программатор** (подключаемый модуль) на основе проекта https://github.com/adafruit/Standalone-Arduino-AVR-ISP-programmer/;
1. Загрузка и проверка .hex файлов. Прошивка .hex файлами AVR чипа;
1. Редактирование fuse битов AVR чипа по маске;
1. **SWD программатор** для STM32 (подключаемый модуль) на основе проектов https://github.com/atc1441/ESP32_nRF52_SWD , https://codeberg.org/blackmagic-debug/blackmagic ; 
1. **UDP-широковещание** для обнаружения устройства в сети (подключаемый модуль) через вспомогательное приложение;
1. **OTA-клиент** для автоматического получения обновлений с сервера (подключаемый модуль);
1. **GPIO-модуль** для управления пинами через веб-интерфейс (подключаемый модуль);

Прошивка для микроконтроллеров **ESP8266** и **ESP32** предназначенная для:

## Система версионирования

В проекте реализована автоматическая система версионирования как для самой прошивки ESP, так и для каждого модуля (ядра и подключаемого) в отдельности. Система основана на Python-скриптах, которые запускаются на этапе сборки PlatformIO.

### Формат версии

Версия прошивки формируется по шаблону:

```
MAJOR.MINOR.DATE.BUILD
```

Где:
- **MAJOR** (1 цифра) — мажорная версия, задаётся вручную в `version_counter.txt`
- **MINOR** (3 цифры) — минорная версия, задаётся вручную в `version_counter.txt`, автоматически увеличивается при изменении git-коммита
- **DATE** (13 символов) — дата и время сборки в формате `ГГГГММДД_ЧЧММ` (например, `20260403_1610`)
- **BUILD** (4 цифры) — номер сборки, автоматически увеличивается при каждой компиляции

Пример полной версии: **`0.015.20260403_1610.0595`**

### Файлы счётчиков версий

| Файл | Назначение | Формат |
|------|-----------|--------|
| **version_counter.txt** | Хранит MAJOR и MINOR версию | Две строки: первая — MAJOR (0-9), вторая — MINOR (0-999) |
| **build_counter.txt** | Хранит номер сборки BUILD | Одна строка: число от 0 до 9999 |

**version_counter.txt** редактируется вручную. При изменении содержимого git-коммита (появлении новых файлов или изменении существующих) скрипт `2_version_builder.py` автоматически увеличивает MINOR на 1.

**build_counter.txt** увеличивается автоматически при каждом запуске сборки. Если файл отсутствует — создаётся со значением 0.

### Генерация version.h (2_version_builder.py)

Скрипт `python/2_version_builder.py` запускается **до** компиляции (pre-script) и генерирует файл `src/version.h`, который содержит макрос `FIRMWARE_VERSION` с полной строкой версии.

**Алгоритм работы:**

1. Читает `version_counter.txt` — получает MAJOR и MINOR
2. Читает `build_counter.txt` — получает BUILD
3. Получает текущую дату/время в формате `ГГГГММДД_ЧЧММ`
4. Получает информацию о git-репозитории:
   - Имя ветки
   - Хеш текущего коммита (первые 7 символов)
   - Флаг "грязного" репозитория (есть несохранённые изменения)
   - Имя тега, если есть
5. Сравнивает хеш текущего коммита с сохранённым в `.last_commit_hash`
6. Если коммит изменился — увеличивает MINOR на 1 и обновляет `version_counter.txt`
7. Увеличивает BUILD на 1 и сохраняет в `build_counter.txt`
8. Генерирует `src/version.h`:

```c
#ifndef VERSION_H
#define VERSION_H

#define FIRMWARE_VERSION "0.015.20260403_1610.0595"
#define FIRMWARE_VERSION_MAJOR 0
#define FIRMWARE_VERSION_MINOR 15
#define FIRMWARE_VERSION_DATE "20260403_1610"
#define FIRMWARE_VERSION_BUILD 595

#define FIRMWARE_GIT_BRANCH "master"
#define FIRMWARE_GIT_COMMIT "a1b2c3d"
#define FIRMWARE_GIT_DIRTY false
#define FIRMWARE_GIT_TAG ""

#endif // VERSION_H
```

**Защита от двойного запуска:** скрипт проверяет, не был ли он уже запущен в текущей сессии (через переменную окружения `VERSION_BUILDER_RUN`). Это предотвращает повторное увеличение BUILD при перезапуске сборки PlatformIO.

### Генерация модульных версий (3_module_version_gen.py)

Скрипт `python/3_module_version_gen.py` запускается **до** компиляции (pre-script) и генерирует файлы `*_version.h` для каждого модуля (как core, так и module).

**Алгоритм работы:**

1. Сканирует директорию `src/` на наличие папок `core_*` и `module_*`
2. Для каждой найденной папки:
   - Вычисляет git-хеш содержимого папки (хеш от конкатенации хешей всех файлов в папке)
   - Сравнивает с сохранённым хешем в файле `.module_hashes`
   - Если хеш изменился — увеличивает версию модуля на 1
   - Получает дату последнего коммита для файлов модуля
3. Сохраняет актуальные версии в файл `.module_versions`
4. Генерирует `*_version.h` для каждого модуля, например `src/core_wifi/core_wifi_version.h`:

```c
#ifndef CORE_WIFI_VERSION_H
#define CORE_WIFI_VERSION_H

#define CORE_WIFI_VERSION "1"
#define CORE_WIFI_VERSION_DATE "20260403"

#endif // CORE_WIFI_VERSION_H
```

**Файлы состояния:**
- `.module_versions` — хранит текущие версии всех модулей (числовые значения)
- `.module_hashes` — хранит git-хеши содержимого каждого модуля для отслеживания изменений

### Именование файлов прошивки и ФС

После успешной сборки бинарные файлы копируются в директорию `proj_fwbins/` с версией в имени:

**Файл прошивки:**
```
{ENV}-FIRMWARE-{VERSION}.bin
```
Пример: `esp32-swd-FIRMWARE-0.015.20260403_1610.0595.bin`

**Файл файловой системы:**
```
{ENV}-FILESYS-{VERSION}.bin
```
Пример: `esp32-swd-FILESYS-0.015.20260403_1610.0595.bin`

Где:
- `{ENV}` — имя окружения (таргета) из `platformio.ini` (например, `esp32-swd`, `esp8266-gpio`)
- `{VERSION}` — полная строка версии из `FIRMWARE_VERSION` макроса

Копирование выполняется скриптами:
- `python/6_copy_fw.py` — копирует `firmware.bin` → `proj_fwbins/{ENV}-FIRMWARE-{VERSION}.bin`
- `python/7_copy_fs.py` — копирует `spiffs.bin` (или `littlefs.bin`) → `proj_fwbins/{ENV}-FILESYS-{VERSION}.bin`

## Python-скрипты сборки

Все скрипты находятся в директории `python/` и подключаются к процессу сборки PlatformIO через параметр `extra_scripts` в `platformio.ini`. Скрипты разделены на **pre-scripts** (выполняются до компиляции) и **post-scripts** (выполняются после компиляции). Число в имени файла (`1_`, `2_`, …) — порядок выполнения. Утилиты `module_registry_gen.py`, `gen_page_head.py`, `build_all.py` запускаются другими скриптами или вручную, поэтому номера не имеют.

### 1_registry_pre_build.py

**Назначение:** Перегенерация списка модулей `src/modules_registry.cpp/.h` под текущий env.

**Тип:** Pre-script

**Алгоритм:**
1. Определяет имя текущего окружения (env) из PlatformIO
2. Запускает `python/module_registry_gen.py --env <env>` (см. [Inclusion mechanism](#inclusion-mechanism))
3. При ошибке генератора — прерывает сборку

### 2_version_builder.py

**Назначение:** Генерация файла `src/version.h` с версией прошивки и информацией о git-репозитории.

**Тип:** Pre-script

**Подробный алгоритм:**

1. **Чтение счётчиков версий:**
   - Открывает `version_counter.txt`, читает первую строку как MAJOR (0-9), вторую как MINOR (0-999)
   - Открывает `build_counter.txt`, читает число BUILD (0-9999)
   - Если файлы отсутствуют — создаёт их со значениями по умолчанию (MAJOR=0, MINOR=0, BUILD=0)

2. **Получение даты сборки:**
   - Использует `datetime.now().strftime(DATE_FORMAT)`, где `DATE_FORMAT = "%Y%m%d_%H%M"`
   - Результат: строка вида `20260403_1610`

3. **Получение git-информации:**
   - Выполняет `git rev-parse --abbrev-ref HEAD` — имя ветки
   - Выполняет `git rev-parse --short HEAD` — короткий хеш коммита (7 символов)
   - Выполняет `git status --porcelain` — проверка на "грязный" репозиторий
   - Выполняет `git describe --tags --exact-match HEAD` — имя тега (если есть)

4. **Автоувеличение MINOR:**
   - Читает файл `.last_commit_hash`
   - Сравнивает с текущим хешем коммита
   - Если хеши отличаются — увеличивает MINOR на 1 и обновляет `version_counter.txt`
   - Сохраняет текущий хеш в `.last_commit_hash`

5. **Автоувеличение BUILD:**
   - Увеличивает BUILD на 1
   - Сохраняет новое значение в `build_counter.txt`
   - Если BUILD превышает 9999 — сбрасывает на 0

6. **Генерация version.h:**
   - Формирует строку версии: `f"{MAJOR}.{MINOR:03d}.{DATE}.{BUILD:04d}"`
   - Записывает файл `src/version.h` с макросами препроцессора

7. **Защита от двойного запуска:**
   - Устанавливает переменную окружения `VERSION_BUILDER_RUN=true`
   - При повторном запуске проверяет эту переменную и пропускает увеличение счётчиков

**Параметры (константы в начале скрипта):**
- `MAJOR_DIGITS = 1` — количество цифр MAJOR
- `MINOR_DIGITS = 3` — количество цифр MINOR
- `BUILD_DIGITS = 4` — количество цифр BUILD
- `DATE_FORMAT = "%Y%m%d_%H%M"` — формат даты

### 3_module_version_gen.py

**Назначение:** Генерация файлов `*_version.h` для каждого модуля (core_* и module_*).

**Тип:** Pre-script

**Подробный алгоритм:**

1. **Сканирование модулей:**
   - Обходит директорию `src/`
   - Находит все папки, начинающиеся с `core_` или `module_`
   - Для каждой папки проверяет наличие исходных файлов (`.cpp`, `.h`)

2. **Вычисление хеша модуля:**
   - Для каждого файла в папке модуля вычисляет git-хеш: `git hash-object <file>`
   - Конкатенирует все хеши через пробел
   - Вычисляет MD5 от полученной строки — это хеш содержимого модуля

3. **Сравнение с сохранёнными хешами:**
   - Читает файл `.module_hashes` (если существует)
   - Сравнивает текущий хеш с сохранённым
   - Если хеш изменился — увеличивает версию модуля на 1

4. **Получение даты модуля:**
   - Выполняет `git log -1 --format=%cd --date=format:%Y%m%d <папка_модуля>`
   - Получает дату последнего коммита, затрагивающего файлы модуля

5. **Сохранение состояния:**
   - Записывает актуальные версии в `.module_versions`
   - Записывает актуальные хеши в `.module_hashes`

6. **Генерация `*_version.h`:**
   - Для каждого модуля создаёт файл вида `src/<module_name>/<module_name>_version.h`
   - Пример: `src/core_wifi/core_wifi_version.h`

### 4_fs_builder.py

**Назначение:** Подготовка и сборка образа файловой системы (ФС).

**Тип:** Pre-script

**Подробный алгоритм:**

1. **Определение окружения:**
   - Получает имя текущего окружения (env) из PlatformIO
   - Определяет тип ФС (SPIFFS или LittleFS) из конфигурации

2. **Чтение версии:**
   - Пытается прочитать версию из `version_counter.txt` + `build_counter.txt`
   - Если не удалось — читает `FIRMWARE_VERSION` из сгенерированного `src/version.h`
   - Формирует полную строку версии

3. **Подготовка директории ФС:**
   - Создаёт директорию `web_debug/web_<env_name>/` (или `web_debug/` для debug-сборок)
   - Копирует все файлы из `data/` в подготовленную директорию
   - Копирует файлы из `web/` папок подключённых модулей (если есть)

4. **Генерация `_version_fs.json`:**
   - Собирает информацию о версии, git, модулях
   - Подсчитывает статистику по файлам (количество, размеры)
   - Записывает JSON-файл в подготовленную директорию

5. **Генерация `page_head.html`:**
   - Вызывает `gen_page_head.py` для генерации динамического заголовка страниц
   - Заменяет маркер `<!-- MODULES_RIGHT_COLUMN -->` на ссылки модулей

6. **Перенаправление PROJECT_DATA_DIR:**
   - Устанавливает переменную окружения `PLATFORMIO_FS_DATA_DIR` на подготовленную директорию
   - Это заставляет PlatformIO собирать образ ФС из нестандартной директории

7. **Запуск сборки ФС:**
   - Вызывает PlatformIO для сборки образа ФС: `pio run --target buildfs --environment <env>`
   - Реализована логика повторных попыток при сбоях (retry)

8. **Создание симлинка web_current:**
   - Создаёт символическую ссылку `web_current`, указывающую на последнюю собранную директорию

### gen_page_head.py

**Назначение:** Динамическая генерация HTML-заголовка страниц (`page_head.html`) на основе подключённых модулей.

**Тип:** Вызывается из `4_fs_builder.py`

**Подробный алгоритм:**

1. **Сканирование модулей на наличие меню:**
   - Для каждого модуля (core_* и module_*) проверяет наличие файла `web/_menu.html`
   - Если файл найден — читает его содержимое как пункт меню

2. **Автоматическая генерация ссылок:**
   - Если `_menu.html` не найден, сканирует `.html` файлы в `web/` папке модуля
   - Извлекает заголовки из HTML-файлов (по тегу `<title>` или первому заголовку)
   - Генерирует ссылки вида: `<a href="page.html">Название страницы</a>`

3. **Сборка итогового HTML:**
   - Читает шаблон `data/page_head.html`
   - Находит маркер `<!-- MODULES_RIGHT_COLUMN -->`
   - Вставляет сгенерированные ссылки модулей вместо маркера
   - Записывает результат в подготовленную директорию ФС

### 5_set_fs_data_dir.py

**Назначение:** Перенаправление директории данных для сборки ФС.

**Тип:** Pre-script

**Алгоритм:**
- Читает переменную окружения `PLATFORMIO_FS_DATA_DIR`, установленную `4_fs_builder.py`
- Устанавливает `PROJECT_DATA_DIR` в PlatformIO на значение этой переменной
- Это заставляет PlatformIO использовать подготовленную директорию (с `_version_fs.json` и сгенерированным `page_head.html`) вместо стандартной `data/`

### 6_copy_fw.py

**Назначение:** Копирование бинарного файла прошивки в директорию `proj_fwbins/` с версией в имени.

**Тип:** Post-script

**Алгоритм:**
1. Получает имя окружения (env) из PlatformIO
2. Читает `FIRMWARE_VERSION` из сгенерированного `src/version.h`
3. Формирует имя файла: `{ENV}-FIRMWARE-{VERSION}.bin`
4. Копирует `.pio/build/<env>/firmware.bin` → `proj_fwbins/{ENV}-FIRMWARE-{VERSION}.bin`
5. Если директория `proj_fwbins/` не существует — создаёт её

### 7_copy_fs.py

**Назначение:** Копирование бинарного файла файловой системы в директорию `proj_fwbins/` с версией в имени.

**Тип:** Post-script

**Алгоритм:**
1. Получает имя окружения (env) из PlatformIO
2. Читает `FIRMWARE_VERSION` из сгенерированного `src/version.h`
3. Определяет тип ФС (SPIFFS или LittleFS) из конфигурации
4. Формирует имя файла: `{ENV}-FILESYS-{VERSION}.bin`
5. Копирует `.pio/build/<env>/spiffs.bin` (или `littlefs.bin`) → `proj_fwbins/{ENV}-FILESYS-{VERSION}.bin`
6. Если директория `proj_fwbins/` не существует — создаёт её

### Порядок выполнения скриптов

При сборке проекта PlatformIO выполняет скрипты в следующем порядке:

**Pre-scripts (до компиляции):**

```
1. 1_registry_pre_build.py → генерирует modules_registry.cpp/.h под текущий env
2. 2_version_builder.py    → генерирует src/version.h (MAJOR.MINOR.DATE.BUILD)
3. 3_module_version_gen.py → генерирует *_version.h для каждого модуля
4. 4_fs_builder.py         → подготавливает директорию ФС, генерирует _version_fs.json и page_head.html
5. 5_set_fs_data_dir.py    → перенаправляет PROJECT_DATA_DIR на подготовленную директорию
```

**Компиляция:** PlatformIO компилирует исходный код в `firmware.bin`

**Post-scripts (после компиляции):**

```
6. 6_copy_fw.py → копирует firmware.bin → proj_fwbins/{ENV}-FIRMWARE-{VERSION}.bin
7. 7_copy_fs.py → копирует spiffs.bin → proj_fwbins/{ENV}-FILESYS-{VERSION}.bin
```

**При сборке образа ФС (Build Filesystem Image):**

```
1. 4_fs_builder.py        → подготавливает директорию, генерирует _version_fs.json и page_head.html
2. 5_set_fs_data_dir.py   → перенаправляет PROJECT_DATA_DIR
3. PlatformIO buildfs     → собирает образ ФС из подготовленной директории
```

## Загрузка прошивки (UART/OTA)

### UART

Панель плагина PlatformIO:
- **Upload** — прошивка ESP через USB/UART;
- **Upload and Monitor** — прошивка + запуск монитора после окончания.

### OTA

Если ESP работает в режиме **ТОЧКИ ДОСТУПА**, подключитесь к ней и через браузер зайдите на `http://192.168.4.1/update.html`.

Если ESP работает в режиме **КЛИЕНТА** Wi-Fi, веб-страницы доступны по адресам:
- `http://<имя>_<серийник>.local/update.html` (например, `http://esp8266_a001.local/update.html`);
- или по IP-адресу, выданному точкой доступа.

---

## Загрузка образа файловой системы

Панель плагина PlatformIO:
- **Build Filesystem Image** — сборка образа ФС на основе директории `data`;
- **Upload Filesystem Image** — загрузка файла образа ФС по UART.

> [!WARNING]
> **ВНИМАНИЕ! После любой манипуляции с UART микроконтроллера происходит перезапуск!**

## Первое включение

Если не были прописаны настройки ТД Wi-Fi в .json файлы, то через минуту после включения ESP сама перейдёт в режим ТД. В списке Wi-Fi сетей появится ТД с именем по умолчанию (например, `ESP8266_A001`) и без пароля. Подключившись к этой ТД, можно зайти на главную страницу по адресу `http://192.168.4.1/`.

---

## Резервирование точек доступа

ESP при включении сканирует эфир в течение заданного времени (настраивается в `config_sys.json`). Если в эфире присутствует одна из прописанных ТД, происходит подключение к ней. Можно настроить до четырёх ТД с индивидуальными настройками DHCP/статический IP.

---

## Веб-авторизация

Для предотвращения несанкционированного доступа предусмотрена авторизация по логину и паролю. Пароль запрашивается при первом обращении к любой странице ESP. Этот же пароль служит для доступа к ESP в режиме ТД.

## Список веб-страниц
